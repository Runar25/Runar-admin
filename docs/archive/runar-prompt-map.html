How Rúnar Speaks — the reading-prompt map

Rúnar · reading-prompt reference · mapped, not changed

How Rúnar speaks

Every reading is built from three stacked layers of text, handed to claude-opus-4-8, and returned as one flowing paragraph. This maps each layer, quotes the real text, and marks what you can tune, what is canon, and what only looks alive.

This map tracks production. Redrawn 2026-09-20 against RUNAR_PROMPT_VERSION = v4.36-most-cil. Newest first (2026-09-20, the reading got a fixed shape): the prompt now builds toward four sentences — scene · the scene one step on · the essence · the bridge. The length draw is gone (it had been running 50/50 between three and four, so half of all readings were a sentence short of the shape the design describes). The ending is no longer a plain draw: what the seeker came for decides its shape — Clarity gets a line, Confirmation two possibilities, Reflection a question, and Insight into Challenge gets the hard wording even on a light rune, because someone who asks for insight into difficulty should not be handed comfort. The area decides where it lands: "in a slow change in the seeker", "where the seeker’s way divides", and six more. A heavy rune forces the hard wording but never changes the shape. The essence line is drawn from two frames: the old one, and a new one where the rune is the one doing something in the scene, named in that same sentence — because the old pairing (say what the rune DOES + mention it by name) makes the copula <Rune> is X, measured 3/3 even in hand-written readings. And the name of the person lost its "early" slot: sentence one already carries the angle, the place and the image, so the name goes mid-reading or beside the bridge. Two blind spots in our own tooling surfaced here: the golden harness pins Math.random to 0.5, so it sees exactly one item from every pool, and its fixtures carry free-text area and seeking rather than the canonical values — it showed zero difference for the whole bridge change. Draw coverage therefore lives in smoke ㉨, which draws for real. Earlier (2026-09-20, the season line is gone and the ending turns to the person): the SEASON line was deleted outright — function and labels with it. It had been in the prompt for one day, and the owner caught it pushing the year into rooms: "A child crosses the late-summer floor" — "it takes up space; in a room that is a completely unimportant fact." Measured: 34 of the 108 image rows (31 %) are register D — domestic scenes, so a third of all readings were told a season that had nowhere to land. Season did not leave the product: it still decides which image may be drawn (RUNE_IMG_SEASONS against the month), it is just no longer an instruction in the text. Whoever revives it has to solve the indoor scenes first. And the ending is now a BRIDGE TO THE PERSON instead of a line that stays in the image: it names what this may be in the seeker’s life — a state offered to weigh, never advice. Three shapes are drawn for light runes (a line · two possibilities · a question); heavy runes get their own shape, said without comfort. The reason is a reader complaint: of an ending held inside the image the owner said "nothing much surfaces for me from it — I cannot even say what it belongs to." Two known flaws sit recorded in the code beside the pool: the question shape steers 2/6, and a version without "may be" killed the possibility shape 2/2. The mechanism. The reader loads the character from the Supabase table runar_character (active row) on every session — app.js — and if an active row exists it replaces the file DEF_CHAR entirely (the quoted text above is then not what Claude receives, and the IS/EN character switch is bypassed; only the voice profile still varies by language). The character editor (the shrine's Rúnar lab) is retired — but the loader was not, so a leftover active=true row from the old lab would silently ship as the voice while everyone edits the file DEF_CHAR in vain. Check the runar_character table, not the shrine: no active row → the file DEF_CHAR is live and this map is exact; an active row → that row is the real voice, and the dead loader should be removed.

Word corrections — one live path, one dead one

live  getCorrPrompt appends a directive block into the prompt (character.js), fed from the Supabase runar_corrections table (edited in the shrine). This is the only correction mechanism that reaches Claude. knob flag CORRECTIONS_IN_PROMPT = true.

the correction block · character.jsWord corrections (follow strictly): — Never say "{from}" — say "{to}" instead {context}

gone  applyISCorrections — the "4th layer" substring post-processor — was deleted on 2026-08-09, together with its CORRECTIONS_POSTPROCESS flag. It had been disabled since 2026-07-10, but was still called on the returned text at five places, so the code read as though corrections were being applied when they were not. It was context-blind (no case, no gender), which is why corrections live in the prompt instead. There is no fourth layer, and none should be added — the rule now has exactly one home, CLAUDE.md §2.

What each reading rolls — and what gets written down

Five things are drawn fresh for every single reading. They are distribution levers, not rules: none of them forbids anything. The point is that two readings of the same rune do not come out the same — so what matters is the spread, never driving any one number to zero.

Since 2026-08-10 the five ARE persisted — readings.prompt_draws stores {kws, name, angle, image, ending, lens} (lens 1/0 since 2026-09-19 — whether the closing lens ran) on the row, so a production reading can be traced back to the door it came through. Verified on the tester export: 23 of 307 rows carry it — every reading from v1.5 on. The paragraph below describes the state before that and is kept because most of the corpus predates it.

Before that: A row in readings carries the deterministic inputs — rune, life rune, area, seeking, intention, question, language, spread, prompt_version, address, mode — and the text. It carries no record of which angle or which image was drawn. So for readings that came out of production (tester batches via export_readings.js) you can measure what the text looks like, but you cannot say which door it came through. Probe batches from gen_batch.js carry the whole prompt, so there the angle and image are recoverable — that is why it also accepts --angle to force one.

Two consequences worth keeping straight. First: an angle gets roughly one seventh of a batch, so 25 readings give about three per angle — far too few to tell whether a change to one angle did anything. Forcing the angle is the only way to measure one. Second: because the draws are not stored, correlating a production reading back to its angle needs the draws to be recorded on the row first. Until then, tester batches answer "how do the readings read", not "which lever caused this".
