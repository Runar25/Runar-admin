Rúnar · reading-prompt reference · mapped, not changed

How Rúnar speaks

Every reading is built from three stacked layers of text, handed to claude-opus-4-8, and returned as one flowing paragraph. This maps each layer, quotes the real text, and marks what you can tune, what is canon, and what only looks alive.

This map tracks production. Redrawn 2026-08-14 against RUNAR_PROMPT_VERSION = v2.0. Newest first: the world description no longer appears twice. 01

The base voice — system prompt

buildSysPrompt(activeChar, lang) · character.js. Sent on every reading, before any per-reading content. Sets who speaks, the tone, the hard bans, and the IS grammar rules. Carries no rune, area, moon or season — those arrive in Layer 2.

  3. Personality — patience of old stone, warmth of a hearth; inhabits mysticism, never performs itDEF_CHAR.personality
  4. Purpose — gather context, make it personal, never genericDEF_CHAR.purpose
  5. How you speak — the live voice profile (spliced from config)VOICE_PROFILES.focused · config.js

✅ Checked — the file DEF_CHAR is what ships. The owner ran select id, active from public.runar_character where active=true on 2026-08-07: no rows, so the quoted character text below is genuinely what Claude receives. Keep the check in mind whenever this map is redrawn — here is why it matters.

The mechanism. The reader loads the character from the Supabase table runar_character (active row) on every session — app.js — and if an active row exists it replaces the file DEF_CHAR entirely (the quoted text above is then not what Claude receives, and the IS/EN character switch is bypassed; only the voice profile still varies by language). The character editor (the shrine's Rúnar lab) is retired — but the loader was not, so a leftover active=true row from the old lab would silently ship as the voice while everyone edits the file DEF_CHAR in vain. Check the runar_character table, not the shrine: no active row → the file DEF_CHAR is live and this map is exact; an active row → that row is the real voice, and the dead loader should be removed.
02

The reading stack — one single reading, in order

buildReadingPromptSingle(u, drawn, lang, corrections) · character.js. A two-pass string: a raw context header, then a stack of directives. Empty factors are silently dropped. This is the exact order the model reads.

  1. PERSON: {name}RP_SINGLE.PERSON
  2. LIFE RUNE: {name} — {keywords} · Realm · ElementslifeCtx · _lifeWasDrawn — own reading, and only when the life rune is not the drawn one
  3. DRAWN RUNE: {name} — focus on {3 shuffled keywords} · World · ElementsdrawnCtx
  4. READING PURPOSE: {intention} + Norns time-framing_intentionContext
  5. READING ANGLE — 1 of 7. The angle is the door the reading comes in through: it decides where the text starts and colours the tone, nothing else. Its own header says so — "follow this entry point — let it shape the opening and tone".utils.js · READING_ANGLES / _randomAngle
  6. SEASONAL IMAGE (if one arises) — 1 no-repeat image of the current Icelandic season_seasonalImagery · _runeImageCandidates
  7. DESCRIBE, DO NOT EXPLAIN — say what the rune does, never what it means_describeRule
  8. NO COLD READING — the recognition is the seeker’s: offer the image, never assert what is true or known inside them_noColdRead
  9. LENGTH — "3 short sentences, 38 to 45 words total"RP_SINGLE.length
  10. CLOSING LENS — the life rune shapes ONLY the last sentence or question; the body belongs to the drawn rune. Never named. If it does not reach the ending naturally, it is left out. Sits immediately before the closing instruction — position is the lever._lensContext
  11. DOMAIN — "this reading is about: {area}", through image, never as a topic_domainContext
  12. REGISTER — the stance for {seeking} (confirm / challenge / mirror…)_registerContext
  13. OPENING BRANCH — question-driven vs rune-driven openingRP_SINGLE.qBranch / noqBranch
  14. ENDING SHAPE — heavy rune: stand or ask hard (1 of 2); otherwise 1 of 3 is a question, the rest rest_endingShape utils.js
  15. PRIORITY tie-breaker — drawn rune in front; the "let the lens recede" clause appears only when a lens exists_priorityContext(lensOn, …)
  16. CLOSING — one paragraph, no breaks; {name-placement, ~55% omit} + langInstrRP_SINGLE.closing · _namePlacement
  17. ÁVARP — IS address gender (kk / kvk / hk)_addressContext · IS only
  18. JSON output contract — return ONLY [{"rune","text"}]RP_SINGLE.json

Five small dice per reading — the 3 shuffled keywords, the angle (1 of 7), the image (no-repeat bag, keyed to the rune), the ending pool pick and the name placement (~55% drop the name entirely). Everything else is deterministic from the inputs. What each die decides, and why none of it reaches the database → what it rolls.

Corrections · spreads · the model

The last tail of every prompt, how each spread differs, and what actually answers.

Word corrections — one live path, one dead one

live  getCorrPrompt appends a directive block into the prompt (character.js), fed from the Supabase runar_corrections table (edited in the shrine). This is the only correction mechanism that reaches Claude. knob flag CORRECTIONS_IN_PROMPT = true.

the correction block · character.jsWord corrections (follow strictly): — Never say "{from}" — say "{to}" instead {context}

gone  applyISCorrections — the "4th layer" substring post-processor — was deleted on 2026-08-09, together with its CORRECTIONS_POSTPROCESS flag. It had been disabled since 2026-07-10, but was still called on the returned text at five places, so the code read as though corrections were being applied when they were not. It was context-blind (no case, no gender), which is why corrections live in the prompt instead. There is no fourth layer, and none should be added — the rule now has exactly one home, CLAUDE.md §2.

What each reading rolls — and what gets written down

Five things are drawn fresh for every single reading. They are distribution levers, not rules: none of them forbids anything. The point is that two readings of the same rune do not come out the same — so what matters is the spread, never driving any one number to zero.

Rolled per readingOut ofWhat it decidesWritten to readings?
Reading angle7The door the reading comes in through — where the text starts and its tone.no
Icelandic image81 entries, 2–5 per rune, filtered by season, both languages on the rowThe one concrete picture the reading is allowed. No-repeat bag per rune-set, identity independent of language.yes — the sentence itself
3 keywordsthe drawn rune's list, shuffledWhich facets of the rune are put in front of the model.no
Ending shapeheavy pool (2) or open pool (3)Whether the reading closes on a question or rests on a statement.no — but readable from the text
Name placementpool + ~55% "drop it"Where the seeker's name lands, or whether it appears at all.no — partly readable from the text

None of the five is persisted. A row in readings carries the deterministic inputs — rune, life rune, area, seeking, intention, question, language, spread, prompt_version, address, mode — and the text. It carries no record of which angle or which image was drawn. So for readings that came out of production (tester batches via export_readings.js) you can measure what the text looks like, but you cannot say which door it came through. Probe batches from gen_batch.js carry the whole prompt, so there the angle and image are recoverable — that is why it also accepts --angle to force one.

Two consequences worth keeping straight. First: an angle gets roughly one seventh of a batch, so 25 readings give about three per angle — far too few to tell whether a change to one angle did anything. Forcing the angle is the only way to measure one. Second: because the draws are not stored, correlating a production reading back to its angle needs the draws to be recorded on the row first. Until then, tester batches answer "how do the readings read", not "which lever caused this".

Don't chase these — alive-looking, but not wired

If you go hunting a nuance and land in one of these, it never reaches a real reading.

  • buildSysPromptV2 + DEF_CHAR_V2_EN — the rich "context line / moon phase / seasonal register / hidden world / Norse world layers" system prompt. Lab-only (shrine V2 tab + compare_*.js). Production uses buildSysPrompt. character.js · buildSysPromptV2 · DEF_CHAR_V2_EN · Season still reaches production — but via the per-reading image in Layer 2, not this.
  • READING_ASPECTS / IMAGERY_SOURCES / READING_REGISTERS / RUNE_PLACEMENTS — labelled dead code; only caller was the removed V2 lab preview. utils.js
  • dynamicContext A/B/C (tree / session / voice) in the proxy — gated off, always empty string; turned off 2026-07-04 for stacking conflicting tone directives. index.ts
  • mood — removed factor; no constant, no field, no reader. runar-branch.js
  • deeper_meaning — generated by Claude and parsed, but not stored or shown for single readings. reading.js
